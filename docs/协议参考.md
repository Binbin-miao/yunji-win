## 二、TTGK HID 协议

### 2.1 传输层

- 输入/输出报告长度均为 **64 字节**
- 魔数 `0x4B` 在 Windows HID 中兼作 Report ID，用 `hidapi` 直接写端点即可
- 报文不足 64 字节时**补零**

### 2.2 帧格式

发送帧的第 2 字节区分读/写：

```
写 (Host → Device):  [0x4B, 0x01, CMD, LEN, PAYLOAD..., 0x00 补零至 64]
读 (Host → Device):  [0x4B, 0x80, CMD, ARG..., 0x00 补零至 64]
响应 (Device → Host): [0x4B, 0x80, CMD, ?, DATA..., 0x00 补零至 64]
```

> **关键**：`0x80` 不是固定头部，而是**读请求标志**。同一条 CMD 用 `0x01` 发就是写，
> 用 `0x80` 发就是读。这是理解整套协议的核心。

响应中数据区起点不固定，取决于命令：

| 数据形态 | 数据起点 |
| :--- | :--- |
| 单字节状态量 | `resp[4]` |
| 16 位数值 | `resp[4..5]` |
| 双通道数值 | `resp[5..6]` |

### 2.3 命令表

#### 读命令（`4B 80 CMD`）

| CMD | 功能 | 请求帧 | 响应解析 | 取值 |
| :--- | :--- | :--- | :--- | :--- |
| `0x02` | 麦克风增益 | `4B 80 02` | `int16LE(resp[4..5]) / 256` | 0 ~ 24 |
| `0x03` | DAC 硬件音量 | `4B 80 03` | `int16LE(resp[4..5]) / 256` | 0 ~ 60 |
| `0x0C` | 固件版本 | `4B 80 0C` | `resp[4..]` 按 ASCII 解析 | 如 `"0.8"` |
| `0x11` | 滤波模式 | `4B 80 11` | `resp[4]` | 0 ~ 4 |
| `0x16` | 声道平衡 | `4B 80 16 04 00`<br>`4B 80 16 04 01` | 两次读取，`int16LE(resp[5..6]) / 256` | 见 2.4 |
| `0x18` | LED 状态 | `4B 80 18 01` | `resp[4] == 0 ? 开 : 关` | — |
| `0x19` | 增益档位 | `4B 80 19` | `resp[4] == 0 ? 低 : 高` | 0 / 1 |

固件版本解析规则（官方实现）：从 `resp[4]` 开始逐字节追加，**遇到 `0x00` 或非 `[0-9.]` 字符即停止**。

#### 写命令（`4B 01 CMD LEN ...`）

| CMD | 功能 | 写入帧 | 是否需 `0x04` 提交 |
| :--- | :--- | :--- | :--- |
| `0x02` | 麦克风增益 | `4B 01 02 02 <i16le(level*256)>` | **是**（间隔 10ms） |
| `0x03` | DAC 硬件音量 | `4B 01 03 02 <i16le(level*256)>` | **是**（间隔 10ms） |
| `0x04` | 保存 / 提交 | `4B 01 04 00` | — |
| `0x09` | EQ 单波段 | 见[第三章](#三8-段-eq-算法与封包) | 配合 `0x0A` |
| `0x0A` | EQ 生效提交 | `4B 01 0A 04 00 00 FF FF` | — |
| `0x11` | 滤波模式 | `4B 01 11 01 <mode>` | 否 |
| `0x16` | 声道平衡 | `4B 01 16 04 <ch> <i16le(att)> 00`（两条，ch=0/1） | 否 |
| `0x18` | LED 开关 | `4B 01 18 01 <0=开 / 1=关>` | 否 |
| `0x19` | 增益档位 | `4B 01 19 01 <0=低 / 1=高>` | 否 |

> **注意** 音量与麦克风写入后**必须**再发 `0x04` 提交，否则断电即失效。
> 官方代码在两条命令之间 `Thread.sleep(10)`。

### 2.4 数据编码

#### 音量 / 麦克风
原始值放大 256 倍后按 **16 位小端有符号**写入：

```
payload = int16_le(level * 256)
```

例：音量 `20` → `20 * 256 = 5120` → `0x00 0x14` → 写入帧 `4B 01 03 02 00 14`

#### 声道平衡（值域 −20 ~ +20）

采用**衰减对侧声道**的方式，不提升本侧：

```
value == 0        → 两条命令均不带衰减（L=0, R=0）
value <  0        → 衰减右声道：ch1 帧携带 int16_le(-|value| * 256)
value >  0        → 衰减左声道：ch0 帧携带 int16_le(-|value| * 256)
```

即：

```
帧A: 4B 01 16 04 00 <衰减值2字节> 00
帧B: 4B 01 16 04 01 <衰减值2字节> 00
两条都发，未衰减的一条填 0
```

读取时返 **R − L**（两个通道各自的衰减值相减），因此正值表示偏左、负值表示偏右。

> **推测**：值域上限 `±20` 来自 UI 滑块范围，硬件是否接受更大值未知。

### 2.5 时序要求

```
音量/麦克风写入 → sleep(10ms) → 0x04 提交
EQ 8 段连写    → 段间隔 ~5ms  → 0x0A 生效 → 重设一次音量（官方用于触发 DSP 刷新）
```

读取失败时官方会重试 `get_info_max_retry_time` 次，每次间隔 5ms。

## 三、8 段 EQ 算法与封包

### 3.1 系数生成（Peaking Biquad）

- DSP 采样率固定 **`Fs = 96000 Hz`**

中间量：

$$A = 10^{\frac{gain}{40}}, \quad \omega_0 = \frac{2\pi f_c}{F_s}, \quad \alpha = \frac{\sin \omega_0}{2Q}$$

未归一化系数：

$$b_0 = 1 + \alpha A,\quad b_1 = -2\cos\omega_0,\quad b_2 = 1 - \alpha A$$
$$a_0 = 1 + \frac{\alpha}{A},\quad a_1 = -2\cos\omega_0,\quad a_2 = 1 - \frac{\alpha}{A}$$

全部除以 $a_0$ 归一化。

### 3.2 定点量化

32 位有符号定点，标度 $2^{30}$（Q30）：

$$\text{Fixed}(x) = \text{round}(x \times 2^{30})$$

打包为 5 个 32 位小端整数：`[b0, b1, b2, -a1, -a2]`，共 20 字节。

> 取整使用 `floor(x + 0.5)`（Java `Math.round` 语义），**负数时与 Python `round()` 不同**。

### 3.3 单波段 37 字节报文

`CMD = 0x09`，`LEN = 0x18`（24）：

| 偏移 | 长度 | 字段 | 说明 |
| :--- | :--- | :--- | :--- |
| `0..7` | 8 | 包头 | `4B 01 09 18 00 <band_index> 00 00` |
| `8..27` | 20 | DSP 系数 | 5 × int32LE `[b0, b1, b2, -a1, -a2]` |
| `28..29` | 2 | 中心频率 | uint16LE（Hz） |
| `30..31` | 2 | Q 值标志 | 固定 `C0 00` |
| `32..33` | 2 | 增益 | `[floor(gain*256) & 0xFF, floor(gain) & 0xFF]` |
| `34` | 1 | 类型标记 | 官方恒为 `0x02` |
| `35` | 1 | Offset | 整体偏移量（有符号） |
| `36` | 1 | 尾符 | `0x00` |

### 3.4 关于类型标记（重要）

官方 `EQData.typeList` 是**死数据**：

```java
// 初始化为全 2，之后从未参与任何系数计算
this.typeList = mutableListOf(2, 2, 2, 2, 2, 2, 2, 2);

// 发包时直接硬编码写入 2，未读取 typeList
byteArrayOutputStream.write(new byte[]{2});
```

全应用内 `typeList` 只出现在 JSON 导入导出的字段搬运处，系数计算也只有 `computePeak` 一个函数。
**即官方从未向设备发送过 `2` 以外的类型，硬件是否识别低架/高架完全未知。**

若要在自有设备上验证：写一段小幅度低架（`fc=1kHz, gain=+6dB`），听感应表现为
「低频整体抬升、1kHz 以上不变」。若无变化或异常，说明硬件忽略该字节。

### 3.5 EQ 上传完整流程

```
for i in 0..7:
    write(4B 01 09 18 00 i 00 00 + 29 字节数据)
    sleep(5ms)
write(4B 01 0A 04 00 00 FF FF)      # 生效
vol = read_vol()                     # 生效确认（官方行为）
sleep(10ms)
set_vol(vol)                         # 重设音量触发 DSP 刷新
```

## 四、旋润 (XuanRun) 控制传输协议

### 4.1 USB 请求参数

| 方向 | bmRequestType | bRequest | wValue | wIndex | 长度 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 写 | `0x43` (67) | `0xA0` (160) | `0` | `0x09A0` (2464) | 7 |
| 读 | `0xC3` (195) | `0xA1` (161) | `0` | `0x09A0` (2464) | 7 |

> `bmRequestType` 低 5 位为 `0x03`（recipient = Other，规范保留值），但官方即如此实现且可用。

### 4.2 帧格式

固定 7 字节，写读共用：

```
[0xC1, 0xA6, CMD, ARG0, ARG1, ARG2, ARG3]
```

**读取必须先写后读**：先发送查询帧，等待约 5ms，再用读请求取回 7 字节响应。

### 4.3 命令表

#### 读命令

| CMD | 功能 | 请求帧 | 响应解析 |
| :--- | :--- | :--- | :--- |
| `0xA0` | 固件版本 | `C1 A6 A0 00 00 00 00` | `resp[3]` |
| `0xA2` | 音量 + 平衡 | `C1 A6 A2 00 00 00 00` | `resp[4]`=音量码<br>`resp[5]`=L 码<br>`resp[6]`=R 码 |
| `0xA3` | 状态四合一 | `C1 A6 A3 00 00 00 00` | `resp[3]`=滤波模式<br>`resp[4]`=增益档位<br>`resp[5]`=LED<br>`resp[6]`=Depop |

#### 写命令

| CMD | 功能 | 写入帧 | 取值 |
| :--- | :--- | :--- | :--- |
| `0x01` | 数字滤波模式 | `C1 A6 01 <mode> 00 00 00` | 0 ~ 4 |
| `0x02` | 增益档位 | `C1 A6 02 <level> 00 00 00` | 0 / 1 |
| `0x04` | 硬件音量 | `C1 A6 04 <vol_code> 00 00 00` | **查表**，见 4.4 |
| `0x05` | 声道平衡 | `C1 A6 05 <L_code> <R_code> 00 00` | **查表**，见 4.4 |
| `0x06` | LED | `C1 A6 06 <0=开 / 2=关> 00 00 00` | 注意关灯是 `2` 不是 `1` |
| `0x07` | 防爆音 Depop | `C1 A6 07 <0=开 / 1=关> 00 00 00` | — |

### 4.4 数据编码（查表）

#### 音量：61 项非线性码表

滑块索引 `0..60` 映射到硬件寄存器值，**不是线性关系**。下表为十进制（括号内十六进制）：

```
索引 0..7:    255(FF) 200(C8) 180(B4) 170(AA) 160(A0) 150(96) 140(8C) 130(82)
索引 8..15:   122     116     110     106     102      98      94      90
索引 16..30:   88  86  84  82  80  78  76  74  72  70  68  66  64  62  60
索引 31..44:   58  56  54  52  50  48  46  44  42  40  38  36  34  32
索引 45..60:   30  28  26  24  22  20  18  16  14  12  10   8   6   4   2   0
```

> 前 8 项步进大（粗调），后段步进小（细调），属人工调校曲线。**不能线性推算。**

#### 平衡：37 档，中位 18

滑块 `0..36`，中位 `18` 为左右均衡。码值代表**该声道的衰减量**：

```
L_code[i] = max(0, i - 18)      # 左声道衰减量
R_code[i] = max(0, 18 - i)      # 右声道衰减量
```

| 滑块 | L 码 | R 码 | 效果 |
| :--- | :--- | :--- | :--- |
| 0 | 0 | 18 | 全左（右声道衰减 18） |
| 18 | 0 | 0 | 均衡 |
| 36 | 18 | 0 | 全右（左声道衰减 18） |

> 滑块越大越偏右。与 TTGK 的「衰减对侧」思路一致，都是只降不升。

## 六、容错与校验

### 6.1 响应校验（TTGK）

设备可能存在**上一条命令的延迟回包**，若不加校验会把旧数据当成本次结果。
应丢弃以下响应：

- 长度 < 3
- `resp[0] != 0x4B` 或 `resp[1] != 0x80`
- `resp[2] != 期望 CMD`
- 指定了 arg 校验时 `resp[4] != arg`
- 长度不足以容纳所需字段

> **注意**：官方 `balanceRead` **不校验** arg 回显，直接取 `resp[5..6]`。
> 本项目额外校验 `resp[4] == ch`。**若真机不回显该字节，此校验会导致永远读不到平衡值** ——
> 属未经真机验证的风险点，必要时放宽。

### 6.2 错误分类（旋润）

libusb 错误码按语义分类，便于定位：

| 类别 | errno | 含义 | 可重试 |
| :--- | :--- | :--- | :--- |
| `stale` | −4 `NO_DEVICE` | 句柄失效，设备已重新枚举 | 需重新获取句柄 |
| `unsupported` | −12 `NOT_SUPPORTED`、−9 `PIPE` | 驱动未绑定 / 接口不符 | 否 |
| `timeout` | −7 | 设备未响应 | 是 |
| `io` | −1 | 链路错误 | 是 |

> `NO_DEVICE` 的含义是「**该句柄指向的设备已不存在**」，不是「找不到设备」。

### 6.3 已知硬件限制

- **左右声道独立 EQ**：协议为单套 8 段参数，`0x16` 只是整体 L/R 衰减配对，非分声道滤波
- **EQ 类型**：官方仅用 `0x02`（Peaking），低架/高架编码为推测值

## 附：待厂商文档确认的疑点

以下问题仅靠逆向无法确定，需要厂商固件文档或真机探测：

1. **TTGK 平衡响应的 arg 回显**：`resp[4]` 是否为通道号回显？若不是，需放宽校验
2. **EQ 类型字节 `1` / `3`** 是否被硬件识别为低架 / 高架
3. **旋润音量码表**是否覆盖全部硬件寄存器范围（仅见 61 项）
4. **TTGK 增益档位**除 0/1 外是否支持更多档
5. 各命令的**最短安全间隔**（当前沿用官方的 5~10ms）
